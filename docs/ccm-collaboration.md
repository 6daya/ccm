# CCM 协作架构决策

日期：2026-10-04。本文是重新审视后的推荐架构，不代表所有能力已实现。

CCM 应当是一套本地工作区与受控执行系统：ccm-mate 提供单一对话入口，运行层维护状态和规则，按任务需要使用执行者、检索者和审查者。项目上下文与可验收交付是核心，agent 数量不是产品目标。

## 公开实践与适用边界

- [Cursor Projects，2026-09-10](https://cursor.com/blog/projects)：用户与协调者沟通，项目保留共享上下文并派发工作。这支持统一入口和项目连续性；云端规模、持续后台运行及其产品收益不能移植为 CCM 的承诺。
- [Cursor 模型分工实验，2026-07-20](https://cursor.com/blog/agent-swarm-model-economics)：区分关键规划判断和便宜执行。可借鉴这种能力分工，不能据此保证公司免费模型执行质量，也不适合照搬其大规模 swarm。
- [Anthropic harness 实验，2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps)：逐项检验流程组件，保留仍能改善结果的部分。模型变强时减少流程，不代表免费模型也能删掉相同约束。
- [Anthropic 多代理研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)：宽度搜索可受益于并行与上下文隔离，同时协调会增加 token 和失败机会。
- [Anthropic 运行层架构，2026-04-08](https://www.anthropic.com/engineering/managed-agents)：持久会话、harness 和执行环境可以解耦。CCM 借鉴职责划分，继续使用本地 OpenCode，不引入云服务。

这些是公开产品与工程实践，不能称为“所有团队都在使用”的唯一标准。

## 一种入口，三种职责

用户日常只与 ccm-mate 对话。ccm-mate 是入口身份，而不是一个额外的管理者套在已有 orchestrator 外面。

1. 对话职责：理解目标、识别相关项目、澄清重要歧义、解释计划和费用、交付结果。默认免费模型；遇到需要强判断的任务可请求限定的强模型判断。
2. 运行职责：安装、配置校验与应用、项目登记、权限、预算、任务状态、恢复、工具回执。由程序负责，模型调用结构化能力，不任意发明 shell 命令。
3. 工作职责：按需启用检索、实现、验证或专家能力。采用 OpenCode 原生 task，避免递归派发、第二套调度器和无必要的 agent 对话。

自然语言、slash command、CLI 应共享底层管理能力。用户说“初始化”即可进入同一初始化流程；/onboard 是可选快捷入口，不应成为 agent 工作的依赖。

## 项目与上下文

工作区登记项目名称、仓库路径、入口说明、规则来源、测试方式和允许的 MCP。仓库可以在 projects/ 下，也可以关联外部路径。

项目长期知识保存业务拓扑、模块归属、已确认决策、测试说明及来源版本；每个任务另存目标、验收条件、变更范围、结果和证据。聊天全文与模型总结不能成为唯一真实状态。只加载与当前项目/任务相关的规则，不在每次对话塞入整个工作区。

管理型对话与业务任务即使使用同一入口，也应按任务隔离上下文和权限。进入配置模式不能让正在执行的任务自行扩大预算或修改验收。

## 流程应按任务调整

| 情况 | 建议处理 |
| --- | --- |
| 状态查询、简单事实、规则解释 | 直接处理，不创建完整团队流程 |
| 常规分析或实现 | 一个执行者，使用相关项目检查 |
| 多仓资料相对独立 | 有界并行检索，返回带来源的压缩结果 |
| 公共模块边界、跨仓方案、重要流程设计 | 先收集免费证据，必要时在实现前使用强模型澄清关键判断 |
| 验证失败、来源冲突、语义设计不确定 | 根据具体证据追加审查或升级；限制次数和费用 |

不能只相信免费主模型自报“任务简单”或“我有信心”。程序规则应设置最低检查要求和禁止动作，风险识别可同时使用涉及模块、变更范围、失败回执和来源冲突。无法证明合格时明确报告不足，不把预算耗尽等同于任务完成。

强模型不应承担大范围检索。也不应被永远限制为只读咨询：如果免费模型无法实现某类任务，限定范围和费用的强模型实现可能比多次返工更划算。这需要公司模型实测后开放，当前基线仍只有只读 expert。

## 验收与自我管理

保留公共模块保护、必做检查、费用限额、实际 MCP 回执、独立验证和中断恢复。不要让每个小分析任务都经过完整 scout/planner/builder/verifier 流水线。

新任务可以提出额外验收案例；既有检查不能由业务代理改写来掩盖失败。固定业务不变量与新任务案例应分开登记。Playwright 可以探索新页面，探索结果与已登记检查通过是不同事实。

初始化和配置更新采用：发现现状 → 提出具体配置 → 校验与差异摘要 → 对权限/费用等持久规则确认 → 程序应用并保存版本。常规只读和已授权执行不重复确认。任务使用固定的规则版本，更新不应悄悄改变在途任务的合同。

## 当前代码与待实现项

已有：free/expert 两槽、只读专家、受控原生 task、任务合同、精确范围、状态与回执、预算估算、固定检查、Node Playwright MCP、CLI 恢复；新增依赖安装前可加载的 /onboard 与 workspace-mate 原型、只读工作区检查。

待实现：默认 ccm-mate 的统一自然语言入口、项目目录与上下文分层、受控的对话式配置更新、按风险选择流程、可选的强模型实现、更多公司模型实测。当前用户仍需通过 /onboard 进入向导，并在业务任务中使用 orchestrator。这是原型限制，不是最终推荐体验。

22 项程序测试通过。真实 OpenCode 已检查：没有 harness node_modules 时发现命令与 agent；应用配置保留 provider；重启后向导绑定 free 模型并收紧权限。此项不是实际公司模型对话验收。

此前两项完整任务以受控模型网关和真实 Node Playwright MCP 通过。2026-10-04 增量端到端回归在 OpenCode 加载配置阶段超过 180 秒，未进入模型请求；原因未确定，不能标为通过。真实公司 GLM/Opus 的质量、延迟和费用收益仍未验证。Windows 仍未实机验证。

下一轮验证应比较：单免费模型、免费模型加 CCM、按需混合模型、单高级模型。衡量可验收交付率、关键问题遗漏、返工次数、人工时间、延迟和实际网关账单，不以子代理数量或程序测试通过代替业务效果。
