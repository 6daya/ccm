# 第一次使用 CCM：从安装到日常与贾维斯协作

适用版本：0.3.0（仅 OpenCode V2）。CCM 是你在 OpenCode 中使用的工作台：贾维斯负责沟通与任务协调，常规工作走你确认免费的模型，需要时才使用已配置的受限只读专家。程序负责范围、验收、预算记录、恢复和归档。`.ccm/` 保存 CCM 私有运行数据，`.opencode/` 是 V2 入口，`workspace/` 是业务仓库集合；目前其他 coding agent 还没有适配入口。

**完成本机环境和仓库准备后，大多数日常操作直接跟贾维斯说就行。** 不需要自己选择 scout/builder/verifier，不需要手工切换 GLM/Opus，不需要写任务图或 JSON，也不需要记 slash command。首次模型选择、持久规则授权、真实账单核对和业务判断仍需要你参与。

## 1. 先认识三个位置

```text
ccm/                              ← 进入这个目录启动 OpenCode
  src/ bin/ docs/                 ← CCM 工程，业务任务不能修改
  .opencode/                      ← OpenCode 的原生入口，初始化后加载 ccm.js
  workspace/
    frontend/                     ← 业务仓库，独立 .git、代码、测试和 docs
    backend/                      ← 另一个独立业务仓库
  .ccm/                           ← 本机配置、任务状态、回执，CCM Git 忽略
    archive/<项目ID>/<任务ID>/
      report.md                   ← 自动生成的任务报告
      manifest.json               ← 来源、检查、原回执引用与报告摘要
```

“项目”是你登记的任务范围，可以是一整个业务大仓，也可以是一组相关仓库。例如 frontend + backend 登记为 orders-system，才能执行同时涉及二者的任务。目录存在不等于已授权接入。

```mermaid
flowchart LR
 A[接入项目] --> B[与贾维斯分析或开发]
 B --> C[验收并自动归档]
 C -->|下一需求| B
```

业务代码、测试和长期业务文档属于业务仓库；每次正式成功任务的报告属于 CCM 本机私有档案。CCM 自身的升级在单独开发环境进行。多个业务仓库不会变成一个大 Git 仓，也没有自动跨仓原子提交。

## 2. 第一次准备：需要你或公司开发环境完成

| 准备项 | 需要达到的状态 |
| --- | --- |
| OpenCode | 已安装；本版集成验证使用 V2 2.0.23 |
| Node | Node 22 满足 `^22.22.2`，或 24.15.0 及以上；在 PATH 上可执行 `node` |
| pnpm、ripgrep、Git | 在 PATH 上可执行 `pnpm`、`rg`、`git` |
| 公司模型 provider | 在 CCM 启动的 OpenCode 中可用；知道哪个实际 provider/model ID 免费 |
| 公司依赖源 | 现有 registry 可以获取锁定依赖；CCM 不会切换公共源 |
| 业务仓库 | 已有访问权限；完整 clone/复制，保留独立 Git 与未提交改动 |
| 编码验收环境 | 需要编码时，业务依赖、测试环境和必要服务可运行 |
| 内部 MCP / 浏览器 | 按需准备，只读知识端点；页面验收需要官方 Node MCP 和已有浏览器环境 |

公司 provider/MCP 使用你已有的安全配置方式。不要把密钥发给贾维斯或贴进聊天。业务子仓库自己的 OpenCode 配置不会自动合并到 CCM。模型显示名称不足以判断实际 ID、免费资格或价格，需要公司配置/网关信息。

macOS ARM64 已做工具集成验证；Windows 尚未实机验证。本机 V2 新原生缓存已通过，完整机器/司内冷安装仍待验证，见第 10 节。

## 3. 下载 CCM，放入业务仓库

下载交付的 `ccm-0.3.0.zip` 并解压，或 clone 指定交付分支：

```sh
git clone --branch feat/harness-baseline --single-branch git@github.com:6daya/ccm.git
cd ccm
```

本次版本在 `feat/harness-baseline`，不要默认从 main 安装。ZIP 不含业务代码、密钥、依赖缓存或运行状态。

把完整业务仓库放进 `ccm/workspace/`。例如：

```sh
git clone <你的前端仓库地址> workspace/frontend
git clone <你的后端仓库地址> workspace/backend
```

这里的地址是你自己的实际仓库地址。也可复制现有完整 checkout，包括 `.git` 和已有改动；无需清空或提交改动才能接入。普通不带 Git 的资料文件夹暂不作为业务仓库登记；只复制源码文件而遗漏 `.git` 会被拒绝。符号链接也不支持。CCM 不会替你 clone、reset 或改业务分支。

文中的尖括号是占位提示，执行命令前替换为实际地址、ID 或路径，不要保留尖括号。日常任务优先使用下面的对话示例，CLI 命令仅供故障恢复或高级操作。

## 4. 启动，与贾维斯说“初始化”

在 CCM 根目录运行：

```sh
opencode
```

默认助手是 Jarvis（贾维斯）。首次向导的当前模型来自 OpenCode 原有选择，尚未初始化时不能提前保证免费。先在 OpenCode `/models` 中选择公司已配置、已确认免费的模型；以后 CCM 的常规角色使用登记的免费模型，不需要每个任务重新切换。

直接发送：

> 初始化 CCM。接入 workspace/frontend 和 workspace/backend，作为 orders-system 项目。常规工作使用当前已确认免费的公司模型，专家先关闭。先核对独立 Git 根和已有改动，读取必要的 AGENTS 与项目说明，向我展示保护目录、验收候选及成果位置，再应用配置。不要读取密钥。

贾维斯会检查环境、发现仓库、确认模型与范围，在选定免费模型后安装锁定依赖。缺失 Node/pnpm/rg/Git 时，它会先定位现有版本和 PATH，再按系统查询官方来源，展示版本、校验、下载/安装命令、位置、PATH 和回退方案，经你确认后安装。公司管理环境遵循公司流程，CCM 包安装仍使用已有 registry。你不用手动执行 pnpm install 或 init，不用自己填写配置。

若已经初始化且后来缺少运行时，直接说“检查环境，提供缺失依赖的官方安装方案”。它通过 `harness_environment` 和 `harness_runtime_prepare` 的原生表单维护；先结束或取消所有活动业务任务。只有获批的按序精确命令可执行一次，错误或重启后需重新检查和确认；不会从业务子代理安装。初始化前没有插件，原生 shell 授权与向导规则负责这一步。实际安装仍需在你的目标环境核验。

它会向你确认具体持久规则：项目 ID 和仓库组、保护路径、明确检查命令/必要浏览器步骤、内部 MCP ID、预算，以及可选专家价格。接入只读取 Git 状态和必要元数据，不自动执行发现的 scripts。没有合适的检查时可以先做分析，编码会受阻；不能把“发现了 test script”当作测试已通过。

只读专家默认关闭；开启时需要实际模型 ID、四类公司价格（input/output/cacheRead/cacheWrite）和预算。知识 MCP 当前按配置 ID 开放全部工具，只接入已经保证只读的端点。

确认具体配置后，贾维斯应用初始化。**退出并重新打开一次 OpenCode**，插件在启动时加载。重新打开仍是贾维斯，可以直接说“检查当前项目，继续刚才的目标”。`/onboard`、`/workspace` 只是可选快捷入口。

## 5. 第一项任务先做分析

例如直接说：

> 在 orders-system 项目中，分析订单页面到后端订单接口的链路。先查看必要来源，给出模块责任、关键调用、已确认事实、不确定项和文件位置。暂不改代码。缺少关键业务范围时向我澄清，完成后告诉我报告在哪里。

贾维斯会选择已登记项目、启动有边界的任务、按需派发免费角色并独立验收。项目不明确时会询问，不会默认纳入所有仓库。正式分析任务也需要来源与独立 verifier；“验收通过”代表登记标准下已完成，不等于业务语义永远正确。

内部知识需求可以一起提出：

> 结合已允许的内部知识 MCP 与订单仓库，解释支付状态口径。列出原文来源和更新时间；来源冲突、权限拒绝或未取得的内容明确标注，不用猜测补全。

内部 MCP 真实效果尚待司内验证；当前归档保留 `agent-supplied` 标记，不把代理摘录变成服务器真实性证明。

## 6. 编码与下一轮修改

已有验收配置、业务依赖和服务就绪后，直接说：

> 在 orders-system 中，为订单提交补 traceId。保持公共组件不变，先确认所属业务模块和具体文件。按已登记的检查验收，说明修改、来源、验证及未解决项。

贾维斯明确目标、精确可写文件和验收，builder 写入业务仓库，独立 verifier 运行固定检查。公共模块保护、敏感路径、检查合同与预算由程序约束；不能通过修改检查让失败变成成功。

日常迭代继续正常说：

> 上一版缺少重复点击去重。按最新代码补这一项，保留我已有改动，验收后交付。

这是新需求与新任务合同。若原任务未完成，则先处理恢复或明确取消，不在活动任务中换项目。免费模型遇到有证据的关键歧义时，可以使用已经开启的受限只读专家；专家不能编码，不会自动切换成付费 builder。实际效果与费用仍需真实试跑判断。

**CCM 业务工具当前没有 commit/push、创建 PR、部署或安装业务依赖的入口。** 让贾维斯给出分仓改动与交付说明，再按你已有的 Git/评审/发布方式执行这些操作。单独的 CCM 开发任务获得的 GitHub 授权，不自动变成业务运行时权限。

## 7. 成果、报告与经验在哪里

| 内容 | 实际位置与用法 |
| --- | --- |
| 代码、测试 | `workspace/<repo>/`，用该仓库 Git 查看 |
| 成功任务报告 | `.ccm/archive/<projectId>/<runId>/report.md` |
| 证据清单 | 同目录 `manifest.json`，含报告 SHA256、来源、规则/检查摘要及回执引用 |
| 原始回执/账本 | `.ccm/receipts/`、`state.json`；不要改写它们来规避验收 |
| 浏览器产物 | 已配置 MCP 的输出位置；报告/检查中保留已有引用，不自动搜索与打包截图 |
| 长期经验/业务说明 | 按明确需求维护业务仓库已有 docs，并按原评审流程生效 |

程序完成自动归档，不增加 LLM 请求。档案是导出时快照：估算费用按配置价格计算，实际网关账单仍未知，晚到的主会话用量可能未包含。后续 `report` 可查看最新已观测记录；重试归档不会覆盖已经完成的档案。

报告保留子任务原有风险与未知项、来源真实性标记、检查回执；不扫描业务文件找产物，不备份 provider，不把整个运行目录打包。档案包含业务结果和本机路径，默认私有；共享时自行选择必要内容。

直接问：

> 列出本会话已完成任务的报告路径，以及哪些来源或费用仍待核实。

不强制每项任务写复盘。需要经验时说：

> 这次需要记录一条经验：订单 traceId 应在业务入口生成。给出适用模块、依据和例外；如果项目已有维护位置与文档检查，再提出写入方案。

当前不会自动提取/晋升知识、加载所有历史档案或修改 AGENTS。需要跨会话复用时，把核实的经验作为明确文件范围维护到业务 docs，下一次要求读取对应文档。没有合适文档检查时先保留报告，再通过正常授权登记新检查。新会话不能自动检索任意旧会话的报告；旧任务详情应回到原会话，或由你提供相关且适当的摘要/业务文档。

## 8. 新项目接入与规则调整

将新仓库放入 workspace 后说：

> 接入 workspace/billing，项目 ID 为 billing。先核对 Git 和未提交改动，展示保护范围、检查命令及默认成果位置。确认后登记，不修改已有项目规则。

贾维斯发现候选、展示具体规则，使用登记工具中的原生具体确认表单。回答表单是对真实持久配置的批准，不是每次派发的模型切换。多个仓库需要跨仓分析时，明确登记一个包含它们的项目组。

当前不能通过业务对话应用已有模型/预算/规则/MCP 修改、删除项目或自动创建 worktree。登记仅新增项目/命令检查，不能覆盖旧检查或削弱重叠仓库的必做检查。活动任务期间不允许登记。需要改变既有配置时，让贾维斯先说明具体限制与维护方案，在独立维护环境核对后应用，不要用新增项目绕过旧边界。

## 9. 中断、取消、归档失败

OpenCode 被关闭后，重新进入**原主会话**，直接说“继续，先核对持久状态与实际子会话结果”。已完成工作和专家不会盲目重跑。若不知道会话 ID，可在 CCM 根目录使用可选恢复入口：

```sh
node bin/cli.mjs resume
opencode --session <上一步显示的主会话ID>
```

V2 的完成判定依赖真实 terminal idle；缺少该标记的尝试保留未知状态与费用预留，不自动重跑。专家仅允许一次持久记录的 HTTP 请求，付费 WebSocket 尚不支持。

需要停止时说“取消当前任务并说明尚未核清的费用”。取消不保证供应商停止在途计费，也不自动还原已经写入的业务文件。付费中断的账单未知时，先按公司网关核账；贾维斯不能自行估一个数字来放开重试。高级核账命令见 README。

业务已验收而归档失败时，直接说：

> 继续完成这个已验收任务的归档，只重试导出，不重复业务工作或专家。

程序复用 `harness_complete` 重试。也可离线执行：

```sh
node bin/cli.mjs report --run <任务ID> --archive
```

活动/失败/取消任务可用 `report --run <任务ID> --out <文件路径>` 导出当前快照；只有终止任务可写固定档案，未完成会明确标注。已存在但被改坏的档案不会覆盖，先保留并排查。崩溃可能留下私有 `.pending-*` 临时目录，重试使用新目录，不把残留当完成结果。

状态锁报错时，可运行 `node bin/cli.mjs doctor --repair-lock`；它只清除确认进程不存在的锁，不删除活动锁。不要手改 state.json、金额或验收回执。

## 10. 常见阻塞与正确下一步

| 现象 | 如何处理 |
| --- | --- |
| OpenCode 启动后长时间无响应、还未调用模型 | 按 [冷启动说明](cold-start.md) 保留日志并有界诊断；本机 V2 诊断已通过；司内依赖仍要实际定位，不反复重跑业务任务 |
| 找不到公司模型/节点环境/依赖源不可达 | 按公司环境方式配置；可向贾维斯询问缺项，凭据配置在本机完成 |
| “不是独立 Git 根” | 确认完整业务 checkout 和 `.git`；不要将 CCM 父仓作为业务 Git |
| builder 无可执行检查 | 先做分析，随后确认并登记真实检查与环境；不要登记恒通过命令 |
| 敏感文件或公共模块被拒绝 | 避开凭据，用必要非敏感来源；公共模块变更需独立规则维护/明确方案 |
| 多项目歧义、跨仓访问被拒绝 | 明确项目或授权登记对应项目组；活动任务先结束/取消 |
| 内部 MCP 不可用/来源冲突 | 保留真实错误和未知项；按 [内部 MCP 验证](internal-mcp-validation.md) 核对，不伪造资料 |
| 预算不足或未知付费费用 | 先核账或终止；本地预算不是公司账户总额，硬额度由网关控制 |

敏感路径保护覆盖已初始化业务工具的读取、搜索、上下文、写入和 Git diff：包括 `.env` 及变体、常见认证配置、密钥后缀/目录。完整固定清单见 `src/sensitive-paths.mjs`。它按文件名匹配，不识别所有文档里的机密，也不约束可信检查/MCP 的 OS 权限；初始向导原生读取仍需遵守其引导规则。

## 11. 升级与 CCM 自身迭代

第一次使用直接采用最新包。已有 0.1/0.2.x 工作台时，先在原版本/原位置结束或取消任务、核对付费；保留旧工作台和全部状态。在另一个目录解压 0.3.0，准备完整业务 checkout、依赖和公司配置，重新向导接入并小范围试用。不要覆盖旧 `.team-harness` 或新 `.ccm`、复制带绝对路径的活动状态或同时操作同一份 checkout。没有自动旧配置迁移。

怀疑是 CCM 的问题时，记录具体目标、版本、最少非敏感错误证据、是否重复发生。正常业务贾维斯不能自改 harness；把问题交给独立的 CCM 开发任务，复现一个问题、做最小修复、验证后交付版本。涉及模型行为的改善还要司内真实自然语言试跑。

## 12. 本版完成了什么，哪些还要试用

- 已实现：统一 Jarvis 入口、显式项目组/范围冻结、免费工作与受限只读专家、独立验收、预算记录/恢复；0.2.1 的归档/接入/敏感路径保留；0.3.0 改为原生 V2 插件与 subagent、移除 Slim、私有目录改为 .ccm，新增确认后的运行时维护。
- 已验证：程序边界与归档回归、真实 OpenCode 加载与模拟模型任务、官方 Node Playwright MCP 浏览器流程。详见 [0.3.0 V2 交付](release-0.3.0.md)。
- 待司内验证：真实免费模型能否少干预地完成工作、专家是否降低返工、实际总费用、内部 MCP 与冷安装；按 [试跑方案](company-pilot.md) 先做两个真实免费任务。
- 后续候选：付费修复、更细路由、原生业务 Git 会话与注册的类型/编译检查、worktree、自动经验检索/知识发布、配置迁移与 Windows 实机。依据真实失败选择一项，不一次增加整套架构。

你从“初始化”开始，之后围绕“我要完成什么、在哪些项目、怎样算完成”与贾维斯沟通即可。工具角色、状态记录和自动归档由它与程序承担。
