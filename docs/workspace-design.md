# CCM 工作台布局与行业实践

日期：2026-10-04。结论：CCM 根目录 + workspace/ 仓库集合适合本用户的跨仓分析、集中模型配置和单一对话入口；它不是所有 coding agent 场景的普遍最佳方案。目录集合本身不提供项目隔离、自动上下文或质量保证。

## 官方实践与判断

| 实践 | 官方机制 | 对 CCM 的启示 |
| --- | --- | --- |
| 在实际项目目录工作 | Claude Code 的常见流程从项目根目录启动；OpenCode 的规则从当前目录向上解析 | 单仓编码优先原生项目上下文；父工作台不能冒充自动继承子仓库配置 |
| 按路径加载规则 | Claude Code 按需加载子目录说明，避免启动时装入全部模块规则 | 只加载选定项目及相关文件祖先的 AGENTS.md，保留来源和截断标记 |
| 子代理隔离上下文与工具 | Claude Code 子代理拥有独立上下文、权限和模型；请求仍计入同一用量 | 免费检索返回有限证据；子代理数量不是省钱指标，付费判断仍须受预算约束 |
| 并行写入使用 worktree | Claude Code 官方提供独立 checkout 的并行流程 | 多个编码任务在同一个 checkout 的风险不能靠目录命名解决；本版精确文件冲突保护，worktree 后续再接入 |
| 使用原生扩展 | OpenCode 提供项目插件、配置、SDK 的项目/目录参数 | 不重做一个 agent app；继续使用官方 OpenCode task 和受控工具，工作台统一入口 |

来源：[Claude Code 常见工作流](https://code.claude.com/docs/en/common-workflows)、[项目规则与记忆](https://code.claude.com/docs/en/memory)、[子代理](https://code.claude.com/docs/en/sub-agents)、[OpenCode 规则](https://opencode.ai/docs/rules/)、[OpenCode SDK](https://opencode.ai/docs/sdk/)、[OpenCode 插件](https://opencode.ai/docs/plugins/)、[OpenCode 配置](https://opencode.ai/docs/config/)。以上是官方能力事实，不是“大家都采用 CCM 目录”的证据。推荐布局是针对本需求的工程判断。

## 方案比较

| 形态 | 适合 | 代价 | 本轮选择 |
| --- | --- | --- | --- |
| 每个业务仓库安装插件，在业务根目录启动 | 单仓编码、原生 Git/LSP 体验 | 跨仓上下文、配置和入口需要协调 | 可保留为未来可选接入方式 |
| CCM 根目录 + workspace/ 独立业务仓库 | 多仓分析、知识工作、集中入口与规则 | 必须显式绑定项目、执行路径和 Git 视图 | 当前推荐并实现 |
| 工作台启动多个仓库原生会话/服务，独立 worktree | 大量并行编码、需要各仓库原生 LSP | 连接管理、权限、恢复和用量核对复杂度较高 | 后续按真实需求引入，当前未实现 |

因此采用“集中控制台 + 明确仓库上下文和受控执行”，避免将物理目录集合当成单一业务仓库。业务仓库保留独立 Git、依赖和测试。CCM 的 Git 忽略业务内容；业务代理只获得选定项目的路径权限，不能修改 harness 自身。

## 固定约束与动态选择

预定义：免费/专家槽位及价格、项目 ID 与仓库组、公共模块保护、明确的命令/MCP 检查、预算、证据大小、尝试次数、task 权限。初始化展示并确认；新增项目与新命令检查需要工具授权，不能覆盖已有检查、修改模型/预算或解除保护。

动态：根据用户任务选择已登记项目；有歧义就澄清；选择相关文件与上下文、按需拆任务、根据具体证据决定是否请求有限付费判断。运行层冻结项目和检查，防止模型自行扩大任务范围。只发现新目录不等于授权读取/修改。

业务项目规则是有来源的约束信息。代码、MCP 结果和 AGENTS.md 都不能覆盖 harness 的权限、预算或验收。AGENTS.md 在根到相关模块按路径加载并记录 digest；规则外部变化时拒绝使用旧输入派发或继续写入。

## 与 0.1.0 的差距及本轮交付

| 项目 | 原版 | 0.2.0 |
| --- | --- | --- |
| 业务目录 | 可选 projects/，主要依赖绝对 roots | 标准 workspace/，完整复制或 clone，业务文件不提交到 CCM |
| 项目登记 | 仓库范围列表 | 稳定 ID、单仓/跨仓项目组、相对路径、项目检查 |
| 当前项目 | 没有独立选择 | 主会话选择，多项目歧义必须澄清，状态持久化 |
| 任务范围 | 全部 roots 均可访问 | 开始时冻结，读/搜/写/检查按项目拒绝越界 |
| 模块规则 | 提示要求自行阅读 | 输入自动包含根和相关模块 AGENTS.md，有限长度与 digest |
| 业务 Git | CCM 原生界面容易混淆 | 显式按仓库 status/diff，验证 Git 根，拒绝父 CCM 仓库 |
| 后续接入 | 只读解释，手动改配置 | 获准后新增项目、命令检查和保护；任务期间禁止登记 |
| 配置可移动性 | 多为绝对路径 | 业务路径相对保存；新任务重新解析；旧未完成任务不自动迁移 |
| 运行上下文压缩 | 注入较完整运行记录 | 压缩时只注入恢复索引，完整结果按需读取 |

尚未完成：仓库原生 OpenCode 子会话目录切换、原生 Git/LSP 面板融合、自动 worktree、项目删除/已有检查更新、公司模型质量/费用对照、Windows 实机验收。当前交付使用受控文件工具、按仓库 Git 视图及明确 cwd 的验收来完成任务；不把这些限制写成已具备的原生能力。

## 接入与升级边界

新工作台：取得 0.2.0 代码 → 将独立业务仓库放进 workspace/ → CCM 根目录启动 opencode → 与 Jarvis 说初始化 → 确认项目、免费模型、保护和验收 → 重启一次 → 正常描述任务。模型和 MCP 来自公司已有 OpenCode 配置，不自动继承子仓库的 provider 配置。

初始化后新增项目：目录放入 workspace/ 不会自动扩大权限；Jarvis 发现候选，提出明确范围/检查，然后使用需要工具授权的登记入口。新增别名/仓库组会继承已有仓库的相关必做检查，不能借改名放宽原验收。检查 argv 是用户批准的受信任程序，并非操作系统沙箱；不要把发现的脚本直接登记成可信检查。

已初始化的 0.1.0：不要覆盖旧配置或直接搬迁未完成任务。先在旧目录结束/取消任务、保留状态与费用核对记录，再建立新的 0.2.0 工作台并初始化。当前没有自动旧配置迁移；估算用量属于各工作台，不是公司账户的全局账单额度。

持续建设 harness：在单独的 CCM 开发 checkout 中修改源码，用独立开发配置/另一个 coding agent 验证后升级工作台。业务 Jarvis 不提供自然语言切换到自改运行层的模式。这样保留 harness 开发能力，同时不会让一次业务任务改变自己的执行规则。
